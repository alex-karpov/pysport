# Единый стандарт проверки типа объекта (`object_kind`)

**Дата:** 2026-09-06
**База:** `master`
**Файлы:** `sportorg/models/memory.py`, `sportorg/modules/plugins/manager.py`, `sportorg/modules/live/orgeo.py`, `sportorg/gui/main_window.py`

---

## Контекст

Каждый сериализуемый доменный объект имеет **вид** (kind): `Person`, `Result`, `Group`,
`Course`, `Organization`, `Race`. В JSON и в пакете teamwork едет **имя класса**
(`ResultSportident`), а ветвиться потребителям нужно по виду: восемь имён `Result*`
(`Result`, `ResultManual`, `ResultSportident`, `ResultSFR`, `ResultSportiduino`,
`ResultRfidImpinj`, `ResultSrpid`, `ResultHuichang`) обрабатываются одинаково.

Отображение «имя → вид» нигде не задано один раз. Список из восьми имён продублирован
в кодовой базе десять раз, шестью разными способами.

### Инвентаризация дублирования

| # | Место | Роль | Тип |
|---|-------|------|-----|

| 3 | `memory.py:1708` `Race.index_obj` | имя → индекс | реестр |
| 4 | `memory.py:1854` `Race.update_obj` | «это результат?» | предикат |

| 6 | `live/orgeo.py:246` | «это результат?» | предикат |
| 7 | `live/orgeo.py:290` | «это результат?» | предикат |
| 8 | `live/orgeo.py:374` | «это результат?» | предикат |

| 10 | `teamwork/packet_header.py:6` `ObjectTypes` | имя → код в протоколе | реестр |

Позиции 1–3 и 10 — законные реестры: они сопоставляют имени разные сущности.
Позиции 4–9 — один и тот же предикат, написанный шесть раз. Расхождения уже накопились:
в `orgeo.py` два списка перечисляют имена в разном порядке, в `update_obj` — в третьем;
комментарий `main_window.py:162-163` перечисляет их в четвёртый раз и уже устарел.

### Почему это чинится сейчас

Незакреплённая конвенция в этом коде демонстрируемо гниёт. Правка индекса объектов
(#542, `68f882a3`) была частично отменена месяц спустя двумя не связанными PR-ами (#538,
#540), и это не заметили, потому что не было ни единого источника правды, ни теста-стража.
Добавление нового подкласса `Result` сегодня требует ручной правки десяти мест, и
пропуск любого из них проявляется не ошибкой, а тихо неверным поведением.

---

## Решение: производный реестр видов в `models/memory.py`

Единственный источник правды — `Race.support_obj`, который и так обязателен при
добавлении типа. Вид выводится по **реальной иерархии классов**, а не по написанию имени.

```python
# sportorg/models/memory.py, уровень модуля, сразу после class Race

OBJECT_KINDS = {
    name: "Result" if issubclass(cls, Result) else name
    for name, cls in Race.support_obj.items()
}


def object_kind(object_name: str) -> str:
    """Вид объекта для ветвления. Неизвестное имя возвращается как есть."""
    return OBJECT_KINDS.get(object_name, object_name)


def is_result_object(object_name: str) -> bool:
    """True для Result и любого его подкласса. Для неизвестного имени False."""
    return OBJECT_KINDS.get(object_name) == "Result"
```

Реестр строится на уровне модуля, а не в теле класса: комприхеншен в теле класса видит
только внешний итератор, но не другие атрибуты класса.

### Контракт: мягкий поиск для ветвления, строгий — для данных

Потребители задают типу два несовместимых вопроса, поэтому API два.

**Мягкий (`object_kind`, `is_result_object`).** Не бросает исключений. `plugins/manager`
получает строку из JSON-RPC от стороннего плагина, `main_window` — от возможно более
старой копии программы; падать там нельзя. Мягкость здесь безопаснее, чем у проверки по
префиксу имени: неизвестное имя попадает в собственный вид и отсеивается следующим же
`.get(..., default)`, а не притворяется результатом. Это ровно семантика нынешнего
`_entity_type`, поэтому поведение плагинов не меняется.

**Строгий.** Там, где промах по виду портит данные, а не просто ветвление
(`Race.create_obj` → `support_obj[name]`, поиск в индексе объектов гонки), нужен
`KeyError`. Эти места поднимают исключение сами; реестр их не подменяет и не смягчает.

**`"Race"` не требует особого случая.** Его нет в `support_obj`, `object_kind("Race")`
вернёт `"Race"` через fallback — текущее поведение `_entity_type`, на которое опираются
`ENTITY_METHODS` и `ENTITY_CAPABILITIES`.

## Точки применения

### Предикаты (позиции 4–9)

| Файл | Было | Станет |
|------|------|--------|
| `memory.py:1854` `Race.update_obj` | цепочка `== "Person"` / `in [8 имён]` / `== "Group"` | `kind = object_kind(dict_obj["object"])`, дальше плоские сравнения `kind == ...` |
| `plugins/manager.py:21,145` | `RESULT_OBJECTS` + `_entity_type` | удаляются; четыре вызова (`_method_for_entity`, `_capability_for_entity`, `_validate_entity_update_method`, `_delete_entity`) идут в `object_kind` напрямую |
| `live/orgeo.py:246,290,374` | три литеральных списка | `is_result_object(item["object"])` |
| `main_window.py:164` | список из восьми `ObjectTypes.*.value` | `is_result_object(command.data.get("object", ""))` |

`RESULT_OBJECTS` и `_entity_type` приватны для `manager.py`; тесты обращаются к
`_method_for_entity`, поэтому удаление безопасно.

По `main_window` два уточнения:

- доступ защищённый (`isinstance(command.data, dict)`) — у служебных пакетов `data` бывает
  `None`;
- поведение сохраняется точно: сегодня `ObjectTypes.Race.value` (0) в списке отсутствует,
  значит пакет с целой гонкой пересчёт не запускает; `is_result_object("Race")` тоже даёт
  `False`. Устаревший комментарий на строках 162-163 удаляется.

### Внутренние реестры (позиции 2–3)

`Race.list_obj` и `Race.index_obj` собираются из пяти записей вместо двенадцати:

```python
@property
def list_obj(self):
    lists = {
        "Person": self.persons,
        "Result": self.results,
        "Group": self.groups,
        "Course": self.courses,
        "Organization": self.organizations,
    }
    return {name: lists[kind] for name, kind in OBJECT_KINDS.items()}
```

Аналогично `index_obj`. Оба свойства уже сегодня пересобирают словарь на каждое
обращение, поэтому по стоимости изменение нейтрально.

### Новая зависимость

`orgeo.py` — единственный из затронутых модулей, который сейчас не импортирует `models`
и работает только со словарями. Импорт `is_result_object` эту границу нарушает. Цикла не
возникает: `models.memory` тянет только `settings`, `common.otime`, `language`,
`utils.time`. Соседний `live.py` уже импортирует `race`, так что направление обычное для
проекта. Альтернатива — нормализовать вид в `live.py` и оставить `orgeo` без модели —
добавляет слой ради границы, которая выглядит случайной, а не спроектированной. Принято:
импортировать напрямую.

## Инварианты (для тестов)

1. `object_kind(name) == "Result"` для всех восьми имён `Result*`; `is_result_object` для
   них — `True`.
2. `object_kind(name) == name` для `"Person"`, `"Group"`, `"Course"`, `"Organization"`,
   `"Race"`; `is_result_object` для них — `False`.
3. `object_kind` для неизвестного имени и для `""` возвращает аргумент без изменений и не
   бросает; `is_result_object` возвращает `False`.
4. Каждый подкласс `Result` (рекурсивно, включая наследников `ResultSportident`)
   присутствует в `Race.support_obj`.
5. Набор имён `OBJECT_KINDS` совпадает с набором имён `ObjectTypes` за вычетом `Race` и
   `Unknown`.
6. `_method_for_entity` и `_capability_for_entity` дают те же результаты, что до правки,
   включая неизвестные и пустые имена.
7. Ветки результатов в `orgeo` отрабатывают для всех восьми имён `Result*` и не
   отрабатывают для `Person` / `Group` / `Organization`.

## Тесты

Новый файл `tests/test_object_kind.py`: инварианты 1–5.

Инвариант 4 — страж от главного сценария гниения: новый `ResultXxx` добавили, в реестр не
внесли. Обход `Result.__subclasses__()` рекурсивно.

Инвариант 5 — сверка с протоколом. Тест только читает `ObjectTypes` и не связывает его с
моделью кодом: `ObjectTypes` остаётся рукописной таблицей числовых кодов (см. «Вне
скоупа»), но расхождение состава имён ловится на CI.

Инвариант 7 требует **новых** тестов: ветки результатов в `orgeo` сейчас не покрыты
(`tests/test_live.py` содержит один тест на поток), и заменять их вслепую нельзя.
Существующие `tests/test_plugins.py` покрывают инвариант 6.

## Вне скоупа

- `ObjectTypes` и формат пакета teamwork. Числовые коды едут по проводу; две копии разных
  версий должны понимать друг друга, поэтому значения заморожены, а таблица остаётся
  рукописной. Связь со стандартом — только читающий тест (инвариант 5).
- Формат файла гонки (`to_dict` / `backup/json.py`): поле `object` продолжает содержать
  имя класса. Вид нигде не сериализуется.
- `isinstance`-проверки в `memory_model.py` и `score_calculation.py`: они работают с
  объектами, а не с именами, и в дублировании не участвуют.
- `SystemType` и вообще различение подтипов результата между собой. Стандарт отвечает
  только на вопрос «какого вида объект», а не «какой системой отметки он получен».

## Зависимость: ветка `fix/teamwork-object-index`

Ветка вводит `Race._index_bucket` с проверкой `obj_name.startswith("Result")` — ровно то,
что стандарт отменяет. Работы не пересекаются, порядок влития любой:

- стандарт первым — ветка при ребейзе использует `OBJECT_KINDS` вместо своего
  `_index_bucket`;
- ветка первой — `_index_bucket` удаляется в пользу реестра, `_index_list_attr` сводится к
  пяти записям, как `list_obj`.

В обоих случаях это правка одного метода и не влияет на объём настоящей работы.
